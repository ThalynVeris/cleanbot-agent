# CleanBot 项目精讲与面试手册

> 目标不是背代码，而是让你能回答四件事：为什么做、请求怎样流动、为什么这样取舍、数据证明了什么。

## 一、先用一句话讲清项目

这是一个面向扫地机器人的垂直客服 Agent：FastAPI 接收流式请求，LangGraph 根据意图进入知识问答、设备月报或环境建议分支；知识问答使用向量检索、BM25、RRF 和 Rerank 找证据，模型只能基于证据生成带引用回答；会话、用户和设备月报使用 SQLAlchemy 持久化，并通过固定评测集验证优化是否有效。

不要说“我训练了一个大模型”，因为本项目没有训练模型；不要说“生产级高并发”，因为目前是单实例原型；可以说“我完成了一个有工程、效果和失败处理闭环的可部署原型”。

## 二、教程版到底做了什么

原版调用链：

```text
Streamlit 输入
  → ReactAgent.execute_stream
  → LangChain create_agent
  → 模型决定是否调用工具
  → rag_summarize / fetch_external_data / weather 等工具
  → 模型整合最终回答
```

### 1. `app.py`

原版用 `st.session_state["message"]` 显示历史消息。问题是 `execute_stream(prompt)` 只传入当前 `prompt`，UI 看起来有上下文，但模型根本没有拿到历史。这是“展示状态”和“模型状态”混淆。

`capture` 是生成器：它逐段消费 Agent 返回内容，再逐字符 `yield` 给 Streamlit。`yield` 不会一次性返回并结束函数，而是暂停函数，下次继续从暂停处运行。这就是流式输出的基础。

### 2. `ReactAgent`

`create_agent` 根据系统提示词和工具描述决定下一步动作。所谓 ReAct 可以理解为模型反复执行“判断需要什么信息 → 调工具 → 观察结果 → 继续回答”。框架已经封装了循环，原代码并没有手写 ReAct 算法。

原版报告流程让模型调用一个没有业务返回值的 `fill_context_for_report` 工具，中间件看到工具名后修改 `runtime.context`，随后动态切换提示词。它能演示 middleware，但业务控制依赖模型“记得按顺序调用”，不够确定。

### 3. RAG

原版流程是：

```text
问题 → Chroma Top-3 → 拼接文本 → 第二次模型调用做概括 → 概括作为工具结果 → Agent 再生成
```

缺点不是“多一次调用”这么简单：第二个模型概括后，原始文档 ID、页码、分数和逐条证据消失，后面很难做引用校验和检索评测。

### 4. 中间件与装饰器

`@tool`、`@wrap_tool_call`、`@before_model` 和 `@dynamic_prompt` 都是装饰器。装饰器接收函数并返回包装后的函数，在不修改调用方的情况下增加工具描述、日志或动态提示词行为。

面试若问“装饰器是什么”，不要只说“语法糖”。可以说：装饰器本质是高阶函数或可调用对象；`@decorator` 等价于 `func = decorator(func)`，常用于横切关注点，例如鉴权、日志、缓存和重试。

## 三、当前版本的一次请求怎样流动

以“主刷被宠物毛发缠住怎么办”为例：

1. Streamlit 向 `POST /api/v1/chat/stream` 发送 `session_id、user_id、message、month`。
2. `AgentService` 验证 session 只能属于一个用户，并先保存用户消息。
3. LangGraph 的 `load_context` 从数据库加载最近 12 条历史，真正提供多轮上下文。
4. `IntentRouter` 先走确定性规则；不明确时再请求模型输出 `IntentDecision` 结构。
5. `knowledge` 节点在必要时把“那宠物家庭呢”改写成独立检索问题。
6. Hybrid Retriever 并行执行向量召回和 BM25 召回，用 RRF 合并名次，再调用 `qwen3-rerank`。
7. 工作流把 Top-N 证据转换为 `SourceRef`，并构造只允许依据资料回答的提示词。
8. `AgentService` 一边读取模型 `astream`，一边产生 SSE `token` 事件；此前已经发送 `status` 和 `source`。
9. 完成后保存回答、来源和耗时，发送 `done`。失败则记录错误类型并返回明确失败，不编造结果。

SSE 顺序如下：

```text
status(routing)
status(prepared)
source × N
status(generating)
token × N
done
```

## 四、为什么用显式 LangGraph

通用 Agent 的优点是灵活，缺点是关键业务步骤可能由模型自由决定。设备月报必须满足“用户明确、月份明确、数据存在”三个条件，不适合把正确性完全交给提示词。

当前图有五种意图：

- `knowledge`：检索知识并生成带来源回答。
- `report`：验证月份 → 查询结构化记录 → 检索维护建议 → 生成月报。
- `environment`：查询用户城市实时天气 → 检索环境保养资料 → 生成建议。
- `smalltalk`：直接返回能力说明，不浪费检索和模型成本。
- `out_of_scope`：明确拒绝股票、医疗、编程等无关请求。

LangGraph 的 state 是一个带类型的共享字典。节点只返回自己修改的字段，条件边读取 `intent` 决定下一个节点。这样日志和测试都能看到请求进入了哪条分支。

这个项目没有为了简历使用多智能体。客服问题只有一个业务目标，拆成多个“角色 Agent”会增加提示词、延迟和错误传播，却没有明确收益。

## 五、RAG 全链路

### 1. 文档导入

导入器支持 TXT 和 PDF。每个切片保留：

- `document_id`：由规范化文件名生成，更新同名文件时保持稳定。
- `chunk_id`：文档 ID、序号和内容哈希的组合。
- `source`：文件名。
- `section/page`：章节和 PDF 页码。
- `content_hash`：文件内容和分块版本共同计算。

为什么哈希还要包含“分块版本”？因为文件没变但算法变了，旧向量也必须重建。项目第一次实测时就发现部分文件被错误识别为标题；加入索引版本后可以强制更新，而不是被“文件 MD5 没变”错误跳过。

### 2. 结构化切分

教程版按固定字符切分，容易把一条问答从中间截断。当前切分优先识别 Markdown 标题和 `1.` 编号条目，只有单条内容过长才按字符窗口切分。最终 6 份资料得到 913 个切片。

chunk 不是越小越好：太小会丢失上下文，太大则检索噪声多、重排和模型 token 成本高。这里利用资料本身的“一条 FAQ/故障/保养建议”作为自然语义单元。

### 3. Dense Retrieval

Embedding 把文本映射为向量，语义相近的文本在向量空间里更接近。优点是能匹配不同措辞，例如“滚刷卷猫毛”和“主刷毛发缠绕”；缺点是对精确型号、数字和专有词不一定稳定。

### 4. BM25

BM25 是稀疏词项检索，强调词频、文档频率和文档长度归一化。它擅长精确关键词，例如 `HEPA`、`H13`、`5200mAh`。中文没有空格，项目为中文字符同时建立 unigram 和 bigram，并保留英文数字 token。

### 5. RRF

Dense 分数和 BM25 分数不是同一量纲，直接相加没有可靠含义。RRF 只利用名次：

```text
RRF(d) = Σ 1 / (k + rank_i(d))
```

同一个切片如果在两路召回都靠前，会获得更高融合分数。项目取 `k=60`，这是常见的平滑值，不应声称它对所有数据最优。

### 6. Rerank

召回阶段追求“不漏”，Rerank 阶段对候选逐个判断“能否直接回答问题”，再选 Top-N。当前使用低成本 `qwen3-rerank`；API 失败时回退 RRF，问答不会整体不可用。

实测代价与收益：

| 指标 | Dense 基线 | Hybrid + Rerank |
|---|---:|---:|
| Hit@3 | 98.00% | 100.00% |
| MRR@5 | 0.9233 | 0.9367 |
| 平均检索延迟 | 295.44 ms | 577.51 ms |
| P95 检索延迟 | 357.20 ms | 641.75 ms |

正确结论是“在当前 60 条数据集上效果提升，但平均增加约 282.07 ms 延迟”，而不是笼统说“Rerank 一定更好”。若业务更看重延迟，可以只对低置信问题启用重排。

### 7. 拒答和引用

检索结果低于阈值时直接请求用户补充信息。生成提示词把资料放在 `<references>` 中，并明确资料是数据而非命令，以降低知识库提示注入风险。

`citation_field_validity=100%` 只证明来源字段完整，不等于回答每句话都忠实。当前另做了 10 条跨 6 类问题的分层答案评测：10/10 成功，引用编号正确率 100%，同供应商 LLM Judge 给出的忠实度与相关性均为 100%，平均生成延迟 2019.79 ms，共返回 8116 个答案与 Judge Token。人工逐条复核未发现资料外结论，但样本小且 Judge 与生成器同源，这些数字不能表述为“答案准确率 100%”；下一步应换独立 Judge 并加入拒答专项集。

## 六、数据库与多轮会话

SQLAlchemy 管理五类数据：用户、设备月度记录、会话、消息、知识文档登记。本地 SQLite 便于启动；部署时通过 `DATABASE_URL` 切换 PostgreSQL，业务代码不需要改。

CSV 只在初始化时由 `csv.DictReader` 导入，不再在每次工具调用中手写 `split(',')`。`user_id + month` 有唯一约束，重复初始化只更新，不重复插入。

多轮对话的关键不是 Streamlit 显示历史，而是后端使用 `session_id` 读取历史并传入工作流。数据库还检查一个 session 不能从用户 1001 改绑到 1002，从源头防止演示数据串用户。

当前只保留最近 12 条消息进入上下文，这是简单的窗口记忆。若真实对话很长，可增加滚动摘要或基于主题的长期记忆，但必须评测摘要是否遗漏关键约束。

## 七、异步、流式与外部工具

FastAPI 路由和 Agent 服务使用 `async def`。模型生成、天气 HTTP 请求属于 I/O 等待，异步可以在等待期间服务其他协程。同步的 Chroma 和数据库操作在 API 的重任务处通过 `asyncio.to_thread` 放到线程，避免明显阻塞事件循环。

`async for` 消费模型流，每得到一个 `AIMessageChunk` 就发送一个 SSE token。SSE 基于普通 HTTP 单向推送，聊天生成只需要服务端到客户端，复杂度比 WebSocket 低。

天气工具使用 Open-Meteo：先将城市地理编码，再查询实时温度、湿度和风速；最多尝试两次。失败时返回 `WeatherResult(ok=False)`，系统明确说实时服务不可用，不再返回固定“26 度晴天”。

## 八、工程化和安全边界

- `.env.example` 只列变量名；真实 API Key 不进入仓库和日志。
- 聊天模型使用 `langchain-openai` 连接百炼兼容接口；Embedding 由薄适配器直接调用 DashScope SDK，不依赖已停止维护的 `langchain-community`。
- 日志采用 JSON，记录 request ID、session ID、意图、来源数、延迟和错误类型，不记录完整用户问题。
- 上传只允许 `.txt/.pdf`、限制大小、清理路径，只取 `Path(filename).name`，避免路径穿越。
- 知识库上传/删除由 `X-Admin-Token` 保护，但这只是 Demo 管理令牌，不是 RBAC。
- Docker Compose 提供 API、Web 和 PostgreSQL；Chroma 使用持久化 volume，已在 Apple Silicon 上从空卷完成端到端验收。
- `/health` 同时检查用户表和向量切片，避免“进程活着但知识库是空的”。

## 九、原版问题与修复对应表

| 原版问题 | 根因 | 当前修复 | 面试价值 |
|---|---|---|---|
| UI 有历史、模型无历史 | 展示状态与模型状态分离 | DB 会话 + graph load_context | 解释真实多轮记忆 |
| 三个 Chroma 目录 | `persist_directory` 是相对路径 | 由项目根解析绝对路径 | 可复现性与排错 |
| 根目录向量数为 0 | 写入和读取目录不同 | 唯一版本化集合，health 检查 | 用数据定位线上类故障 |

| 固定假天气 | 没接外部服务 | Open-Meteo + timeout/retry/fallback | 外部 API 失败设计 |

## 十、如何演示项目

三分钟演示顺序：

1. 问“主刷不转怎么办”，展示逐 token 输出和 4 个来源卡片。
2. 追问“那宠物家庭呢”，说明第二问通过历史被改写成独立检索问题。
3. 选择用户 1003 和 2025-03，生成设备月报，指出数据来自数据库，建议来自知识库。
4. 选择不存在的月份或问股票，展示系统拒绝编造。
5. 打开 `/docs` 和 `reports/evaluation/latest.md`，展示 API 契约与实测指标。

不要现场重新构建知识库，避免浪费时间；提前执行 `cleanbot health`，确认 `users=10、documents=6、chunks=913`。

## 十一、面试回答模板

### 一分钟版本

我把一个跟教程完成的 LangChain 扫地机器人客服重构成了可评测的 LangGraph 应用。原版存在假多轮、向量库路径漂移、随机工具数据和来源丢失问题。我将意图路由和报告流程改成显式状态图，使用 SQLAlchemy 保存 10 个演示用户、120 条月报和会话消息；RAG 侧实现了结构化分块、Dense 与 BM25 双路召回、RRF 融合和 Qwen Rerank，并通过 FastAPI SSE 输出带引用回答。60 条评测集上 Hit@3 从 98% 提升到 100%，MRR@5 从 0.9233 提升到 0.9367，同时记录了平均检索延迟从 295 ms 增至 578 ms。项目有 21 项测试、84% 核心覆盖率和经过实机验证的 Docker Compose 部署，但我把它定位为单实例可部署原型，不声称生产高并发。

### 三分钟版本结构

1. 业务问题：客服知识问答、设备月报、环境建议。
2. 原版缺陷：假多轮、路径漂移、随机数据、不可评测。
3. 架构选择：FastAPI + LangGraph + SQLAlchemy + Chroma。
4. RAG 优化：结构切分、Dense/BM25/RRF/Rerank、引用与拒答。
5. 证据：固定数据集指标、测试覆盖率、真实 SSE 冒烟测试。
6. 取舍：效果换延迟、同源 Judge 局限、单实例限制与下一步独立评测。

## 十二、常见追问（30 题）

1. **为什么不用纯 ReAct？** 月报步骤有强约束，显式图更可测、更稳定；知识分支仍保留模型生成能力。
2. **LangChain 和 LangGraph 的关系？** LangChain 提供模型、消息、工具等抽象，LangGraph负责有状态节点和条件边编排。
3. **什么叫假多轮？** UI 显示历史不代表模型拿到历史；原版每次只提交当前问题。
4. **为什么历史只取 12 条？** 控制 token、延迟和旧话题干扰；这是窗口记忆的简单实现。
5. **为什么不直接把全部文档塞给模型？** 上下文有限、成本高、噪声大，也无法稳定引用。
6. **为什么同时用 Dense 和 BM25？** Dense 擅长语义改写，BM25 擅长型号、数字和精确词。
7. **为什么不直接加两个分数？** 两种分数尺度不同；RRF 使用名次，避免强行校准分数。
8. **Rerank 与 Embedding 区别？** Embedding 适合大规模快速召回；Rerank 对少量 query-document 对做更精细相关性判断。
9. **为什么只返回 4 个来源？** 控制上下文噪声和生成成本；候选阶段仍召回更多切片。
10. **Hit@3 是什么？** 前三条中至少有一条人工标注相关文档的查询比例。
11. **MRR 是什么？** 第一条相关结果名次倒数的平均值，更奖励相关结果排在第一。
12. **为什么 Hit@3 100% 不等于回答 100% 正确？** 检索到了证据，模型仍可能误读或生成无依据内容。
13. **评测集如何避免作弊？** 标注后冻结测试集；调参数使用单独开发集，不根据测试失败逐题补规则。
14. **当前数据集有什么偏差？** 很多问题来自同一批资料，真实用户口语、错别字和跨文档问题仍不足。
15. **为什么索引哈希包含分块版本？** 分块算法改变时，即使文件没变也必须重建向量。
16. **如何支持文档更新？** 稳定 document ID 定位旧切片，内容哈希变化时先删除旧向量，再写新切片和登记。
17. **如果写新向量失败怎么办？** 当前单机版本会抛错并保留错误日志；更严谨可先写新版本集合，成功后原子切换 alias。
18. **为什么 SQLite 和 PostgreSQL 都支持？** SQLite 降低本地门槛，PostgreSQL 更适合部署和并发连接；通过 SQLAlchemy 隔离差异。
19. **SSE 和 WebSocket 怎么选？** 本项目主要是服务端单向 token 推送，SSE 更简单；需要双向实时控制时再用 WebSocket。
20. **异步解决什么问题？** 在模型和 HTTP I/O 等待时释放事件循环，不等于让 CPU 密集任务自动变快。
21. **同步 Chroma 会阻塞吗？** 会，因此 API 重操作使用 `asyncio.to_thread`；大规模场景可改为独立检索服务。
22. **天气 API 失败怎么办？** 最多两次请求，返回结构化失败并停止生成实时结论，不使用固定假数据。
23. **如何防 Prompt Injection？** 系统指令与资料分隔、资料声明为不可信数据、限制工具和业务范围；仍需持续红队评测。
24. **为什么日志不记完整问题？** 减少隐私和密钥泄露；用 request ID、意图、耗时和错误类型定位问题。
25. **10 并发能证明高并发吗？** 不能，它只用模拟模型验证会话不串；真实吞吐需在供应商限流下压测。
26. **Docker 解决什么？** 固化 Python、系统依赖和服务组合，减少环境差异；它不自动让架构变成微服务。
27. **为什么不加 Redis？** 当前单实例数据量没有明确缓存或分布式锁需求，为堆技术栈加入只会增加运维成本。
28. **为什么不做微调？** 主要问题是私有知识、流程和可追溯性，RAG 与工作流更合适；没有高质量训练集时微调收益不确定。
29. **下一步最值得做什么？** 用独立 Judge 扩大答案/拒答评测、冻结真正持出集、记录真实首 token 指标，以及基于低置信度的条件 Rerank。
30. **项目最有价值的排错是什么？** 发现有效库有 584 条向量，但应用读取的根目录库为 0；根因是相对路径随工作目录变化，最终改成绝对路径和 health 检查。
