# M0.1 修复 Rerank 默认策略：代码、文档与评测结论必须一致

## 1. 问题

评测报告（`docs/EVALUATION.md` 第 3 节）基于 60 条验证集得出结论：`disagreement` 策略在 Hit@3 持平的前提下，把 Rerank 调用减少 52%、平均检索延迟降低约 27%，README 也写明它是「最终策略」。

但代码的默认值是另一回事：

```python
# cleanbot/core/config.py（修复前）
policy = (value or "always").strip().lower()
```

`.env.example` 里同样写的是 `RERANK_POLICY=always`。结果是：任何人按 README 复制 `.env.example` 启动，跑的都是**评测中被淘汰的策略**，而文档声称的延迟和调用收益不会出现。

## 2. 修改（🟢 复制级）

| 文件 | 改动 |
|---|---|
| `cleanbot/core/config.py` | 未设置 `RERANK_POLICY` 时默认 `disagreement` |
| `.env.example` | `RERANK_POLICY=disagreement` |
| `tests/test_config_and_database.py` | 新增 `test_rerank_policy_defaults_to_evaluated_disagreement_strategy` |

测试写法值得记住：

```python
monkeypatch.delenv("RERANK_POLICY", raising=False)  # 确保走默认值分支
get_settings.cache_clear()                           # get_settings 有 lru_cache，必须清缓存
try:
    assert get_settings().rerank_policy == "disagreement"
finally:
    get_settings.cache_clear()                       # 不污染其他测试
```

## 3. 为什么（精读题）

1. 为什么 `get_settings()` 要用 `@lru_cache`？它给测试带来了什么麻烦？
2. 为什么测试里用 `monkeypatch.delenv(..., raising=False)`，而不是直接不设置？（提示：CI 或开发机环境里可能已有该变量。）
3. 为什么 `tests/conftest.py` 中的测试夹具仍然显式写 `rerank_policy="always"`，这次不需要改？（提示：夹具是给确定性单测用的，和运行时默认值是两件事。）

## 4. 面试可讲的点

> 「我在复盘项目时发现评测选出的最优策略没有落到默认配置里，文档和运行行为不一致。我补了一条默认值测试，保证以后评测结论和运行时配置不会再次漂移。」

这体现的是 JD 里的「AI 系统评测设计」：评测结论必须能落地到配置，并被测试保护。
